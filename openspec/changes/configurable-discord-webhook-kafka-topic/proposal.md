# Proposal: deliveryMode on NotificationRequest (SDK side)

## Intent

beacon-api is adding an optional `deliveryMode` so a producer can record a notification without delivering it to Discord. Today `notificationRequestSchema` is a `z.strictObject`, so a consumer passing `deliveryMode` gets a VALIDATION `BeaconError` and the field never reaches the wire.

This is the consumer/client side of a two-repo coordinated capability. The field name, its two tokens, and absent ⇒ `DELIVER` are **frozen** by the beacon-api proposal (Engram `sdd/configurable-discord-webhook-kafka-topic/proposal`, project `beacon-api`). Do not rename or extend them here.

Success: a consumer can send `deliveryMode: 'RECORD_ONLY'` on any transport, and every existing request still compiles and serializes byte-identically.

## Scope

### In Scope
- `deliveryMode?: 'DELIVER' | 'RECORD_ONLY'` on `NotificationRequest` and `notificationRequestSchema`.
- `SUPPORTED_CONTRACT.deliveryModes`, mirroring the existing `channels` entry.
- README usage and contract table.
- Unit tests: both tokens accepted, unknown token rejected, omission preserved, pass-through on all three transports.

### Out of Scope
- Any destination/webhook/URL field — permanently.
- A `BeaconConfig`-level or client-level default for `deliveryMode`.
- Surfacing beacon-api's new `SKIPPED` status in `NotifyResult`; `notify()` reports acceptance, not outcome.
- The known `kafka.defaultTopic` duplication with beacon-api.

## Capabilities

### New Capabilities
- None.

### Modified Capabilities
- `notification-publishing`: `NotificationRequest` gains one optional closed-enum field, validated client-side, forwarded unchanged.
- `transport-selection`: its "Transport port" requirement bans per-notification destinations; it needs an explicit statement that a delivery *mode* token is not a destination and the webhook ban is unchanged.

## Approach

- **Additive core change only.** Verified: all three adapters serialize the whole validated request (`JSON.stringify(request)`, `postJson(url, request)`, `variables: { input: request }`), so no transport code changes.
- **Never defaulted client-side.** Omitted stays omitted on the wire; beacon-api applies `DELIVER`. Follows the established `dedupeKey` convention: forwarded unchanged, never generated by the SDK.
- **Per-request only.** A config-level default would silently mute a whole service; `BeaconConfig` is the transport surface, not a payload surface.
- **SSRF mitigation preserved.** The field carries a closed two-token enum, never a URL, address, or destination. `z.strictObject` keeps rejecting webhook fields.
- **Versioning.** Additive-only, no compile break: MINOR bump, not MAJOR.

## Affected Areas

| Area | Impact | Description |

Public API surface: `NotificationRequest` (widened, source-compatible), `SUPPORTED_CONTRACT` (one added key). No removals or renames.

## Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| SDK ships before beacon-api accepts the field: REST/GraphQL reject, Kafka drops silently | Med | Release after beacon-api deploys; state the minimum beacon-api version |
| Field drifts from the frozen upstream contract | Low | Tokens frozen upstream; spec phase asserts exact values |
| `RECORD_ONLY` misread as "delivered" | Low | Document that it suppresses channel delivery |
| Change slug names a webhook/topic feature, not `deliveryMode` | Low | Keep the slug for cross-repo correlation; artifacts use the real name |

## Rollback Plan

Revert the commit. The field is optional and additive, so no consumer payload or stored data changes shape. If already published, release a patch reverting the type, schema, and `SUPPORTED_CONTRACT` entry; consumers passing `deliveryMode` fall back to a VALIDATION error, the pre-change behavior. beacon-api needs no coordinated rollback: it still treats an absent field as `DELIVER`.

## Dependencies

- beacon-api accepting `deliveryMode` on the Kafka ingest, REST, and GraphQL DTOs (sibling change, same slug).

## Success Criteria

- [ ] `deliveryMode: 'DELIVER' | 'RECORD_ONLY'` validates; any other value raises a VALIDATION `BeaconError` naming the field.
- [ ] Omitting it leaves the serialized payload byte-identical to today on all three transports.
- [ ] The field is present in the payload sent by REST, GraphQL, and Kafka when supplied.
- [ ] No destination, URL, or webhook field exists anywhere in the public API.
- [ ] `pnpm vitest run` and `pnpm typecheck` pass.
